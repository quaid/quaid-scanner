# quaid-scanner v0.1.5

**Released:** 2026-09-10

## What's New

### Agent-Session Provenance

quaid-scanner is built to be driven by an agent, and v0.1.5 lets the agent sign its work.

A new `--provenance-file <path>` flag accepts a JSON record of the agent session that produced a
scan — the model(s) used, token counts, a session ID, an agent ID, and a timestamp. The scanner
embeds it, unchanged, in the report:

- **JSON output** gains a top-level `provenance` object.
- **Markdown output** gains a `## Report Provenance` section rendered as a readable table.

It is entirely opt-in. When no provenance file is supplied, no `provenance` key appears in the JSON
and no section appears in the markdown — existing output is byte-for-byte unchanged.

```bash
echo '{"models":["claude-opus-4-8"],"inputTokens":12450,"outputTokens":3210,"totalTokens":15660,"sessionId":"sess_abc123","agentId":"karsten-ospo","generatedAt":"2026-09-10T14:23:00-07:00"}' > /tmp/prov.json

quaid-scanner . --format json --quiet --provenance-file /tmp/prov.json
```

If the file is missing, malformed, or doesn't conform to the `ProvenanceInfo` shape, the scanner
emits a warning and continues without provenance — a bad provenance file never aborts a scan. The
`ProvenanceInfo` type is exported for library consumers who want to construct it programmatically.

This is the foundation for the agent-first scan → report → backlog workflow: a report can now carry
a machine-readable record of exactly which model generated it and at what cost.

### quaid-scanner Took Its Own Medicine

A health scanner that scores poorly on its own criteria is hard to trust. Between v0.1.4 and
v0.1.5, quaid-scanner closed several real gaps its own scanners had been flagging:

- A **`GOVERNANCE.md`** documenting the maintainer-led model, how decisions are made in the open,
  and the path to adding maintainers.
- A **`FUNDING.yml`** Sponsor link (Open Collective).
- A **CI workflow** that runs lint, build, and the full test suite with coverage on every pull
  request — so the 80%+ coverage gate is enforced, not just aspirational.
- **GitHub Actions pinned to commit SHAs** instead of moving tags, closing a supply-chain gap
  ([#123](https://github.com/quaid/quaid-scanner/issues/123)).

The self-scan score did not rise as a result — see the breakdown below for why, and why that is
the honest outcome.

### Accuracy: Four Field Defects, Found by Using the Tool

The release was ready on 2026-08-02. Running it against a real external project —
[LMCache](https://github.com/LMCache/LMCache), 142 SHA-pinned actions, a multi-stage CUDA
Dockerfile, a 109 MB virtualenv — found four defects severe enough to hold the publish for five
weeks. Each is the same shape: **the scanner penalised the more sophisticated setup.**

- **The published binary did nothing at all.**
  ([#222](https://github.com/quaid/quaid-scanner/issues/222)) A global install printed nothing and
  exited 0 on every invocation, because npm links `bin` as a symlink and the entry-point guard
  matched on the filename. Exit 0 with no stderr is the worst possible shape: a CI job gating on
  `--threshold` read it as a clean pass and silently approved every repo. It was invisible in
  development and to a 97.9%-coverage test suite, because every test invoked `dist/cli.js`
  directly. Tests now invoke the built binary through a symlink.

- **SHA-pinned actions were reported as unpinned.**
  ([#221](https://github.com/quaid/quaid-scanner/issues/221)) The `uses:` parser swallowed the
  trailing `# vX.Y.Z` comment — the documented OpenSSF convention, and exactly what Dependabot
  writes when it updates a pinned action. 142 of 166 findings on LMCache were false, and the
  suggested remediation was to do what the project had already done.

- **Multi-stage Docker builds were misread.**
  ([#236](https://github.com/quaid/quaid-scanner/issues/236)) `FROM base AS release`, referring to
  a stage declared earlier in the same file, was reported as an untagged external image. There is
  no image to tag, so the advice was impossible to act on. 13 of 15 Docker CRITICALs were false.

- **Python virtualenvs were scanned in full.**
  ([#223](https://github.com/quaid/quaid-scanner/issues/223)) 701 findings came from third-party
  package source, including CRITICALs on pip's own bundled wheels.

**LMCache rescan, same commit:**

| | Before | After |
|---|---|---|
| `dep-pinning-docker` WARNING | 166 | 27 |
| `dep-pinning-docker` PASS | 0 | 142 |
| Security CRITICALs | 23 | 11 |
| Findings inside `.venv/` | 701 | 0 |

The headline score is unchanged at 2.3/10, because the pillar formula saturates at four CRITICALs
([#241](https://github.com/quaid/quaid-scanner/issues/241)). Removing 155 false findings should
move a score. That it does not is the next thing to fix.

These four are now tracked as **Epic 14: Scanner Accuracy & Field Hardening** in the PRD — the
place this category of work belongs, which it did not previously have.

## Bug Fixes

- **Response-time and response-classification scanners no longer error against GitHub's GraphQL
  API** — Both ordered an inner `comments` connection by `CREATED_AT`, which `IssueCommentOrderField`
  no longer accepts; GitHub rejected the whole query and every finding degraded to a WARNING carrying
  the API error. The invalid ordering is removed, and GitHub's default comment order preserves
  first-response timing exactly. ([#213](https://github.com/quaid/quaid-scanner/issues/213))

## Under the Hood

- **Consolidated scanner directory exclusions** — Eight scanners each carried their own drifting
  `EXCLUDED_DIRS` lists; they now share one `excludeGlobs()` baseline, closing the drift that had
  reintroduced self-scan and cache bugs. The binary-artifacts scanner intentionally keeps
  `__pycache__` visible so it can still flag committed `.pyc` bytecode.
  ([#171](https://github.com/quaid/quaid-scanner/issues/171))

### Why this is lower than the 8.1 drafted for this release

An earlier draft of these notes claimed **8.1/10 (LOW risk)**, with Community at 7.6. That figure
was measured while the response-time scanners were still broken by the GraphQL regression fixed in
[#213](https://github.com/quaid/quaid-scanner/issues/213). Broken scanners contributed no findings,
so the pillar scored well by not being measured.

Now that they work, they report what is actually true of a solo-maintained project: a **1237-hour
median first response** and **83% of issues with no response at all**. The Community pillar reads
0.0. Fixing a scanner lowered the score — which is the system working, and worth saying plainly in
a release whose theme is trusting the numbers.

Every remaining finding is real:

| Pillar | Finding |
|---|---|
| Security | No required status checks on `main`; OpenSSF Scorecard not yet indexed (HTTP 404, new project); `publish.yml` grants `id-token: write` — deliberate, it is how OIDC trusted publishing works |
| Governance | 75% of commits from one email domain — a bus factor of one |
| Community | 1237h median first response; 83% of issues and 100% of PRs unanswered; 0% casual→regular conversion |
| Inclusive | One `"master"` hit, the README's own "Known false positives" table describing the [#124](https://github.com/quaid/quaid-scanner/issues/124) detection-target-string false positive — the scanner flagging the sentence that explains it |

The security and community gaps are exactly what contributions close.

### A caveat on the headline number

Community reads 0.0 with 2 CRITICALs, and would read 0.0 with 20. The pillar formula
`10 − (C×3 + W×1.5 + I×0.1)` floors at four CRITICALs, so the bottom of the range cannot
discriminate. That is a real limitation of the current scoring, tracked in
[#241](https://github.com/quaid/quaid-scanner/issues/241) — and it is why the LMCache rescan below
still reads 2.3/10 even after this release removed 155 false findings from it.
