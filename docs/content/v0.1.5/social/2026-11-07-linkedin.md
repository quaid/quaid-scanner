# LinkedIn Post: quaid-scanner v0.1.5

---

My open source health scanner raised a CRITICAL finding on my own repository: no required
pull-request reviews. So I enabled them. I am the only committer on that project, and GitHub does
not let you approve your own pull request.

Every merge since has required an admin override of the branch protection rule. That is strictly
worse than not having the rule at all — it trains the one person holding the bypass to use it
reflexively, and it makes the protection meaningless to anyone reading the repository's settings.
The scanner recommended a control the project structurally cannot satisfy, and the project got
less safe by following the advice.

That turned out to be a class of bug rather than a one-off. Only 2 of 43 scanners consulted
project maturity at all, and maturity is the wrong axis anyway: a project can be mature,
well-tested, widely used, and still have exactly one committer. Those are different things, and a
health tool that conflates them will keep producing advice its users cannot act on. So v0.1.5 adds
team-shape awareness. When a repository has no practical second reviewer, "required reviews not
enabled" drops from CRITICAL to INFO and recommends required status checks instead — a control
that one person can satisfy and that genuinely blocks a bad merge. A bus factor of one is still a
real risk and stays visible; what changed is that the severity and the suggested remedy now match
what the project can actually do.

Two implementation details mattered more than I expected. Counting distinct commit email addresses
does not work — this repository's own history has three author addresses and one human, so the
naive version would have reported three committers and left the bug unfixed on the very repository
that surfaced it. And every ambiguity has to resolve toward "not solo": an unknown team shape, a
shallow clone, or a non-git directory all keep the original severity. That last one matters because
GitHub targets are cloned with `--depth 1`, where a naive reading would mark every remote scan solo
and quietly relax security checks across the board.

The rest of the release came from pointing the tool at a real external project and watching it
fail. Four defects, every one the same shape — the scanner penalised the more sophisticated setup.
SHA-pinned GitHub Actions reported as unpinned, which is the documented OpenSSF convention and
exactly what Dependabot writes. Multi-stage Docker builds misread as untagged external images.
Seven hundred findings from inside a Python virtualenv. And worst, a globally installed binary that
did nothing at all: it printed nothing and exited 0, so a CI job gating on a score threshold read
that as a clean pass and silently approved every repository it saw. It was invisible in development
and to a 97%-coverage test suite, because every test invoked the built file directly rather than
the installed binary.

One more thing worth saying plainly. A draft of these release notes claimed 8.1 out of 10, LOW
risk. The published number is 6.5, MEDIUM. The 8.1 came from a scan run without a GitHub token —
five API-backed scanners degrade to a harmless INFO when no token is present instead of recording
themselves as skipped, and the report still says it is complete. The pillars those scanners feed
score well by not being measured. That is a 1.6-point swing across a risk-level boundary, produced
by an environment variable, with nothing in the report disclosing it. It is now filed as a bug and
it is the first thing the next release fixes.

It is easy to publish a number that went up. The test of a health tool is whether you publish the
one that went down because you made the tool more honest.
